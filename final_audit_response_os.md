# AiNxt OS — Open-Source Release Compliance Audit

**Audit target:** `ainxt-os` repository (65-crate Rust workspace, "AiNxt OS" — governed AI runtime), snapshot as a single-commit tree ("Initial commit").
**Audit date:** 2026-09-05
**Audit brief:** `prompt.txt` (forensic OSS compliance / supply-chain / legal-release audit, 27 phases)
**Auditor posture:** Evidence-based only. Every finding below is backed by a file path, a command actually run, or a quoted line. Where something could not be verified, it is marked **UNVERIFIED** or **LEGAL REVIEW REQUIRED**, never assumed safe.

**Important scoping note:** this pass was originally an **audit and remediation plan**, not a silent auto-fix. A subsequent remediation pass (same date, 2026-09-05) then *applied* the mechanical, non-legal fixes from that plan and independently re-verified them with the repository's own tooling — see **§15 (Remediation pass log)** for exactly what changed, what was verified, and what was deliberately left untouched pending Legal/product/human input. Section 12 (below) is preserved as originally written — the plan as it existed *before* remediation — so the delta between "planned" and "actually done" stays visible rather than being silently merged away.

## 0. Executive summary

AiNxt OS has clearly already been through **one serious OSS-readiness pass** — it ships `deny.toml`, `THIRD_PARTY_INVENTORY.yaml`, `THIRD_PARTY_NOTICES.md`, `.gitleaks.toml`, a CI pipeline, a documented Apache-2.0→MIT license migration (`docs/release-readiness/LICENSE-MIGRATION.md`), and unusually candid self-disclosure (README admits the SBOM doesn't exist yet; NOTICE admits the clean-room/independence claim can't be verified from the tree alone; CI comments admit CI was structurally disabled for a period and the test suite silently stopped compiling).

That candor is the single best sign in this repository — but it is also why this audit could **independently confirm, with live commands, that several of the repo's own "already fixed" claims are currently false**, and it surfaced additional gaps the prior pass missed. Concretely:

- **`Cargo.lock` does not exist** in the tree, despite `.gitignore`, `README.md`, `setup.sh`, `deny.toml`'s own CI job, and `THIRD_PARTY_INVENTORY.yaml` all asserting or depending on it being committed. This breaks reproducible builds, breaks the CI `build` job (`cargo build --locked` has nothing to lock against), and makes every dependency-license claim in the third-party documents **unverifiable against the actual resolved graph**. Mid-audit, installing `cargo-deny` forced a fresh resolve, which let us measure the real gap for the first time: the actual dependency graph resolves to **417 locked packages / 323 unique external crates** — the committed `THIRD_PARTY_INVENTORY.yaml` documents only **173**. That freshly-resolved (but still uncommitted) lockfile was then used to run the real `cargo deny` gate — see the next bullet and §5.1.
- **`cargo deny check licenses` was actually run and empirically FAILS today** (exit code 4): `notify` v6.1.1 (pulled in by `ainxt-injection-svc`) is `CC0-1.0`-licensed, and `CC0-1.0` is absent from `deny.toml`'s allow-list. This is no longer a manual prediction — it is the gate's own real output. Not a legal risk (CC0 is public-domain-equivalent, stricter than MIT, imposes no copyleft or attribution duty), but a live, unresolved, empirically-confirmed gate failure. `cargo deny check bans`, `check sources`, and `check advisories` were also run for real and all **passed clean** (no unknown sources, no known RUSTSEC advisories, no yanked/unmaintained crates in the resolved graph) — see §5.1 for full output.
- **`GATE_0_CHECKLIST.md`** — the document `GOVERNANCE.md` names as the mandatory precondition for any release ("No release ships until Gate #0 … is green") — **does not exist in the tree**. By the project's own governance rules, this repository is not releasable as-is.
- Running the repository's **own** CI scripts live (`.github/scripts/check-doc-links.sh`, `check-mermaid.sh`) found **240 broken documentation links** (of 10,240 checked) and **6 unescaped-HTML-entity mermaid diagrams** — directly contradicting `docs/release-readiness/LICENSE-MIGRATION.md`'s own claim of "5070 links checked, 0 broken" / "1268 mermaid blocks scanned, 0 offending lines." Either that record is stale or the docs regressed after 2026-09-01; either way, the **blocking** `docs` CI job would fail today. A deeper look attributes essentially all 240 to an **undocumented, stale, duplicate flat mirror** of the `docs/` corpus (~252 files at `docs/*.md` that shadow the real, correctly-organized `docs/<subfolder>/*.md` tree — the organized tree itself has zero broken links).
- The literal **first command** in `README.md`'s Quick Start — `git clone https://github.com/npci/ainxt-os.git` — points at a URL that **returns HTTP 404**, confirmed with a live fetch during this audit. The same non-resolving URL is also embedded in `Cargo.toml`'s `repository` field. "Install from zero" (Phase 18) fails before the first line completes.
- `NOTICE` and `THIRD_PARTY_INVENTORY.yaml` still contain a **known, previously-identified defect**: they mislabel the DOMPurify component bundled inside `mermaid.min.js` as "MIT-licensed" when it is actually Apache-2.0/MPL-2.0. The project's own migration log records this exact defect being *found and fixed* in `THIRD_PARTY_NOTICES.md` — but the fix was never ported to `NOTICE` or the YAML inventory, which still contradict `THIRD_PARTY_NOTICES.md` and, in the YAML's case, contradict itself two lines apart.
- `NOTICE`'s trademark clause names `AINxt_logo_icon/` as where the brand assets ship. That directory **does not exist** — it was deleted in an earlier cleanup and the assets now live under `assets/`. This is the one section of `NOTICE` that carries actual legal weight (the MIT grant's carve-out for marks), and it points at a folder that isn't there.
- `CHANGELOG.md` is linked twice from `README.md` and does not exist. Separately, `CONTRIBUTING.md` makes two more independently-confirmed false factual claims: it says `ainxt-cli` "is not a workspace member" (root `Cargo.toml` lists it first) and that the workspace has "63 crates" (actual, verified count is 65).
- No secrets, no PII, no NPCI-internal hostnames/credentials/IPs, and no hardcoded single-vendor AI-provider lock-in were found. The deliberate test-fixture secrets (`AKIAIOSFODNN7EXAMPLE`, `sk-abcd…`) are exactly what `.gitleaks.toml` documents and are correctly confined to redaction/egress test code. Telemetry defaults to a no-op sink and the one optional OTLP exporter path uses a non-networking transport in the OSS build — no undocumented external data transmission was found.
- No unresolved AGPL/GPL/LGPL dependency was found anywhere in the dependency surface that could be enumerated without a lockfile. One near-miss (wasmtime's default `component-model` feature would have pulled MPL-2.0 `im-rc`/`sized-chunks`/`bitmaps`) was **already proactively disabled** with the reasoning documented inline — this is the one clearly *good* piece of copyleft engineering found in the audit.
- The independence/clean-room claim in `README.md` ("no source code, identifiers, prompts, comments, file layouts, or terminology were copied") is **honestly flagged by the repository itself as unverifiable from this tree** (the ADR corpus is not published). This audit found no evidence contradicting the claim, but also has no way to positively confirm it — it is carried forward as a **LEGAL REVIEW REQUIRED** item, not resolved either way.
- `NOTICE` and `README.md` **directly contradict each other** on model-weight governance: `NOTICE` claims weight licenses are "tracked in `MODEL_WEIGHTS_REGISTER.md`" and enforced by "ADR-018"; `README.md` says no such register exists because no weights ship in this tree. Neither `MODEL_WEIGHTS_REGISTER.md` nor any `ADR-*.md` file exists anywhere in the repository — so every citation of an ADR number anywhere in this repo (including in `deny.toml` and three crates' source comments) as evidence of a completed governance step is currently unverifiable (F-29).

**Bottom line: `NOT READY — BLOCKED`.** None of the blockers are exotic — they are all mechanical, cheap to fix, and the repository already has the tooling (CI, `deny.toml`, the doc-link checker) to prove the fixes worked. See §13 for the exact release decision and blocker list, and §12 for the fix plan.

- Read every root-level legal/governance file in full (`LICENSE`, `NOTICE`, `THIRD_PARTY_INVENTORY.yaml`, `THIRD_PARTY_LICENSES.md`, `THIRD_PARTY_NOTICES.md`, `deny.toml`, `.gitleaks.toml`, `SECURITY.md`, `MAINTAINERS.md`, `GOVERNANCE.md`, `CODEOWNERS`, `README.md`, `setup.sh`, `config.toml`, `.github/workflows/ci.yml`, `.github/dependabot.yml`, `docs/release-readiness/LICENSE-MIGRATION.md`).
- **Actually executed** the repository's own compliance/CI scripts rather than trusting their prior output: `bash .github/scripts/check-doc-links.sh` (full run, 10,240 links checked) and `bash .github/scripts/check-mermaid.sh` (2,532 mermaid blocks scanned).
- Ran `git ls-files`, targeted `grep`/`rg` sweeps across the **entire tracked tree** (not samples) for: copyleft license names/SPDX tokens, secret-shaped patterns (AWS keys, OpenAI-shaped keys, PEM private keys, GitHub/Slack/Google tokens, JWTs, credentialed connection strings), NPCI-internal indicators (private IPs, internal domains, employee emails, Jira/Confluence/AWS/Kafka identifiers), hardcoded org-identity conditionals, and hardcoded AI-provider endpoints.
- Verified `cargo --version` works (1.97.1). `cargo-deny` was not preinstalled; it was installed mid-audit (`cargo-deny 0.20.2`) and **all four gate checks were actually executed** from repo root: `cargo deny check licenses` (FAILED, exit 4), `check bans` (ok, warnings only), `check sources` (ok), `check advisories` (ok). Installing it forced a fresh dependency resolve, producing a real (if still uncommitted) `Cargo.lock` for the first time in this audit — see §5.1 for the full output and what it changes.
- Independently re-derived every finding below rather than trusting either the repository's self-documentation or any single scan — consistent with the audit brief's instruction not to trust a scanner, a package name, or the repository author's own claim of being open-source-safe.
- Where a claim in the repo's own documents (`README.md`, `NOTICE`, `LICENSE-MIGRATION.md`) could be mechanically checked, it **was** checked, and every mismatch is called out explicitly in §5–§9 rather than silently trusted.

## 2. Architecture snapshot (for context, not a finding)

65 crates, one HTTP daemon (`ainxt-runtimed`, port 8080) fronted optionally by a Console (`ainxt-os`, port 8081). A turn passes: authenticator → session manager → compliance/authz/audit gates → chat surface → model router → provider chain (offline by default) → SSE stream back to caller. Everything fails closed by design (refuses to start without an identity posture chosen; refuses an unauthenticated turn inside the stream rather than at the transport layer). This design is not itself an OSS-compliance concern; it's included only so the findings below have context (e.g., why `AINXT_TRUSTED_GATEWAY`, `SettlementPerimeter`, and the provider adapters look the way they do).

## 11. Items requiring LEGAL REVIEW (not resolvable by engineering alone)

These are carried forward exactly as the repository's own migration record (`docs/release-readiness/LICENSE-MIGRATION.md §6`) already flagged them, plus three additional items this audit surfaced. None of these should be silently decided by an engineer.

1. **Patent grant loss.** Apache-2.0 §3 granted an express patent license with a retaliation clause; MIT contains no express patent grant. The Apache→MIT migration means downstream recipients now receive materially less than before. **Question for legal:** is this loss acceptable/intended, and does it need to be called out anywhere more prominently than the migration doc?
2. **Trademark wording sufficiency.** Apache-2.0 §6 reserved trademarks explicitly; MIT is silent on trademarks, so `NOTICE` now asserts the reservation independently. **Question for legal:** is `NOTICE`'s current trademark language (once F-07's stale path is fixed) actually sufficient/enforceable given this repo ships real brand imagery?
3. **Inbound-contribution relicensing.** `CONTRIBUTING.md` now binds future contributions to MIT; anything contributed under the old Apache-2.0 posture was licensed on those terms. **Question for legal:** since contributions are stated as "not yet open," is this moot, or is there any existing external contribution that needs consent to relicense?
4. **Already-distributed copies.** If any earlier Apache-2.0-licensed drop of this repository was ever distributed outside NPCI, that grant is irrevocable for those copies, and both licenses now exist in the wild for the same code. **Question for legal:** was any pre-MIT snapshot ever distributed externally, and if so, does anything need to be documented about the dual-licensing-in-the-wild situation?
5. **Copyright year inconsistency.** `LICENSE`/`NOTICE` assert 2026; ~758 source headers assert 2024-2026. **Question for legal:** which is correct, and should it be harmonized or left as an accurate reflection of when different files were actually authored?
6. **Independence / clean-room provenance.** `README.md`'s "no source code, identifiers, prompts, comments, file layouts, or terminology were copied" claim is explicitly stated by the repository itself to be unverifiable from this tree (the ADR corpus is withheld). This audit found no contradicting evidence but has no way to positively confirm it either. **Question for legal/compliance:** should the withheld ADR corpus (or a summary/attestation derived from it) be made available to whoever needs to stand behind this claim publicly, given it is the single load-bearing statement for "no proprietary/third-party code was copied"?
7. **`CC0-1.0` policy admission (F-05).** Adding `CC0-1.0` to `deny.toml`'s allow-list is technically trivial but is, by the file's own stated governance, a **policy decision requiring legal sign-off**, not just an engineering patch — CC0 grants no patent rights, which is why some organizations disallow it outright. **Question for legal:** approve (or reject and replace the `notify` dependency instead).
8. **Cross-bank federation disclosure (F-17).** `docs/retrieval_advanced.md:57` and `docs/compliance.md:36,349,360` describe, at a real level of operational detail, a "federation tier" letting NPCI compute mule-account-velocity signals across member banks. **Question for legal/business:** is this level of detail about a fraud-detection capability intended for public disclosure in an open-source repository, independent of any license concern?
9. **Settlement-perimeter default patterns (F-17).** The OSS default hardcodes real Indian payment-rail address patterns (`upi-settlement.`, `neft.rbi`, `rtgs.rbi`, `nach.npci`) as a security-relevant default value. **Question for legal/security:** confirm this default (as opposed to shipping an empty default and requiring every adopter to supply their own) was an intended design decision and not something that should itself be gated behind the enterprise/private tree.
10. **Model-weights governance claim vs. README (F-29).** `NOTICE` states model-weight licenses are "tracked in `MODEL_WEIGHTS_REGISTER.md`" and "enforced at runtime by the model governance gate (ADR-018)"; `README.md` states flatly that no such register exists because no weights are distributed in this tree. Neither `MODEL_WEIGHTS_REGISTER.md` nor any `ADR-*.md` file exists anywhere in the repository. **Question for legal/compliance:** which statement is correct — was a weight-governance register and ADR corpus ever meant to ship with this release, or should `NOTICE` be corrected to match README? Until answered, no claim citing "ADR-018" or the model governance gate anywhere in this repo (including in `deny.toml` and three crates' source comments) can be treated as verified.
